# Runtime compatibility fix 0.1.9 — pgAdmin Tables + PostgreSQL SERIAL

## Symptoms addressed

- PostgreSQL application DML (`SELECT`, `INSERT`, `DELETE`) succeeds through Mapepire, but `CREATE TABLE ... SERIAL ...` fails on Db2 for i with SQL0204 because `SERIAL` is a PostgreSQL pseudo-type rather than a Db2 data type.
- pgAdmin connects and shows schemas, but its **Tables** collection is missing.
- pgAdmin can emit a top-level `SELECT EXISTS(...)`; forwarding that PostgreSQL form to Db2 for i can produce SQL0199 with `EXISTS` as the unexpected token.

## Design correction

### 1. PostgreSQL SERIAL -> Db2 for i identity

The translation pipeline rewrites column type positions only:

- `SMALLSERIAL` / `SERIAL2` -> `SMALLINT GENERATED BY DEFAULT AS IDENTITY`
- `SERIAL` / `SERIAL4` -> `INTEGER GENERATED BY DEFAULT AS IDENTITY`
- `BIGSERIAL` / `SERIAL8` -> `BIGINT GENERATED BY DEFAULT AS IDENTITY`

The rewrite is intentionally column-aware. An ordinary column named `serial` is not rewritten. Db2 for i permits only one identity column per table, so the proxy rejects a PostgreSQL CREATE TABLE containing multiple SERIAL-family columns with SQLSTATE `0A000` instead of sending invalid DDL to IBM i.

`GENERATED BY DEFAULT` is used because it is the closest Db2 for i behavior to PostgreSQL's SERIAL convention: Db2 generates a value when the column is omitted, while an explicit value can still be supplied.

### 2. Live pgAdmin table catalog adapter

pgAdmin 9.17's table browser uses PostgreSQL `pg_class` OIDs and PostgreSQL-only subqueries for triggers, inheritance, descriptions and table properties. Those queries are now intercepted before generic `pg_catalog` rewriting and resolved from live IBM i catalog data:

```sql
SELECT TABLE_SCHEMA, TABLE_NAME, TABLE_OWNER, TABLE_TYPE,
       TABLE_TEXT, LONG_COMMENT, COLUMN_COUNT
  FROM QSYS2.SYSTABLES
 WHERE TABLE_SCHEMA = ?
   AND TABLE_TYPE IN ('T', 'P')
   AND (SYSTEM_TABLE_TYPE IS NULL OR SYSTEM_TABLE_TYPE <> 'S')
 ORDER BY TABLE_NAME
```

The proxy emits stable virtual table OIDs derived from `(schema, table)` so pgAdmin can use the same identifier across count, nodes, properties and post-create lookup calls.

### 3. Scalar EXISTS compatibility

A top-level PostgreSQL form such as:

```sql
SELECT EXISTS(SELECT 1 FROM ... WHERE ...) AS present
```

is rewritten for Db2 for i as a searched CASE predicate with `SYSIBM.SYSDUMMY1` as the one-row source.

### 4. pgAdmin CREATE TABLE ownership batch

pgAdmin may append:

```sql
ALTER TABLE IF EXISTS schema.table OWNER TO pg_role;
```

The proxy acknowledges that locally. Real IBM i ownership remains the configured Mapepire service profile. A pgAdmin CREATE TABLE batch is accepted only when all additional statements are the virtual OWNER statement or basic TABLE/COLUMN comments; PostgreSQL-only privileges, security labels, row-security and storage options remain rejected before partial execution.

## Build-time regression gates

0.1.9 adds:

```text
pgAdmin IBM i table browser contract check OK
PostgreSQL-to-Db2 DDL/scalar translation check OK
```

These verify the table count/node/property/OID contracts plus SERIAL and SELECT EXISTS translation on the compiled JavaScript used by the runtime image.
